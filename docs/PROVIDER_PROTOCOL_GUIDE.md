# دليل بروتوكولات المورّدين | F90 CARD

## ما الذي يعمل فعليًا؟
- **SMM Panel API v2**: طلبات action=services / balance / add / status مع key، بحسب المحوّل الحالي.
- **REST JSON (Bearer Token)**: طلبات JSON بالمصادقة Bearer؛ يجب مطابقة أسماء العمليات والحقول مع المحوّل الحالي، فليس كل REST API متوافقًا.
- **Omega Store**: محوّل خاص، القراءة فقط للخدمات والرصيد حاليًا.
- **Yassen Card**: محوّل خاص مع api-token، تحقق من رابط API الرسمي وحقول الطلبات.
- **F90 Merchant API**: واجهة توزيع منفصلة عن واجهة استيراد المورّدين؛ **لا يوجد محوّل استيراد ذاتي مثبت** حتى الآن.

## تحديد نوع واجهة المورد في أقل من دقيقة
1. اطلب **API Documentation** و **Base URL** الرسميين من المورد.
2. راجع مثال طلب جلب الخدمات، لا ترسل توكنًا عبر عنوان URL عام أو في محادثة.
3. إن ظهر `action=services&key=...` غالبًا SMM Panel. إن ظهر `Authorization: Bearer ...` فهذا **نوع مصادقة** وليس ضمان توافق REST JSON. إن ظهر `api-token` فابحث عن المحوّل الموافق.
4. قارن حقول المنتج: id/name/rate/min/max، وعملات الأسعار، وصيغ إنشاء الطلب وفحص حالته.
5. إذا كان GraphQL أو SOAP أو OAuth 2.0 أو مخططًا مختلفًا، اطلب محوّلًا مخصصًا؛ لا تختر محوّلًا غير مطابق.

## إجراء اختبار آمن
1. أضف المورد وهو **غير مفعّل**، وأبقِ **الطلبات الآلية مغلقة**.
2. أدخل رابط HTTPS الرسمي والتوكن في خانة السر المخصصة فقط.
3. افحص الاتصال والرصيد وقائمة الخدمات بعمليات قراءة فقط.
4. استورد خدمة واحدة كمسودة مخفية؛ راجع السعر والعملة والحدود والحقول.
5. لا تنفّذ شراءً حقيقيًا قبل تجربة مستقلة ومراجعة سجلات المحفظة وتكرار الطلبات.
6. لا تربط F90 بنفسه لتنفيذ طلبات آلية حتى يتوفر كشف للدورات ومنع تكرار الطلبات.

## معلومات مطلوبة من أي مورد جديد
- رابط الوثائق وBase URL
- أسلوب المصادقة (Bearer / API Key / OAuth 2.0)
- أمثلة منقحة لعمليات services, balance, add, status
- عملة الأسعار، حدود المعدل، وأكواد الأخطاء
- هل يدعم Idempotency Key لتجنب الطلبات المكررة؟

> لا تضع المفاتيح السرية في GitHub أو لقطات الشاشة أو ملفات الواجهة. الخيارات الظاهرة في لوحة الإدارة يجب أن تمثل محوّلات تعمل فعليًا، لا مجرد أسماء بروتوكولات.
